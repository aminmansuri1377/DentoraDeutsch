# Dentora · v0.2

Mobile German dental-learning app with a separate desktop administration panel.

**Next.js 16.4.3 stable + App Router**, React 19, TypeScript strict, Tailwind 4, Prisma 7, tRPC 11, Auth.js/NextAuth. Production database: **Supabase PostgreSQL**. Deployment target: **Vercel**.

## Run the complete local test version

```sh
npm ci
npm run db:generate
npm run dev
```

No `.env` file is required for the local test. When DATABASE_URL is absent, the dev launcher creates an embedded PostgreSQL-compatible PGlite database, applies the migration and seeds sample content. Local data persists in `.local-database/`, which is excluded from Git and delivery archives. This mode is single-process and development-only.

- `/anmelden`: enter any valid email to register/sign in immediately, **without a code or email**.
- `/lernen`: real database-backed learner app, deliberately phone-sized (maximum 480px) even on desktop.
- `/panel`: separate desktop administration. Test password: **1111**.
- `/demo`: independent visual sample data; not your database records.

An ephemeral AUTH_SECRET is generated by the dev launcher if none exists. Restarting without a persistent secret invalidates panel cookies. For a stable local secret, set a randomly generated 32+ character AUTH_SECRET in `.env`.

`npm run dev:local` explicitly forces the isolated local database even if DATABASE_URL is set. It does not edit Supabase.

## Administration

All **49 Prisma models** support create, paginated list/search, full details, edit and delete. The panel has shared table, form, field, relation-picker, details and confirmation components. Metadata is generated from the full Prisma schema during `db:generate` and `build` (not from Prisma's reduced runtime metadata). Primary identifiers are immutable on edit; authentication secrets are masked. Relation selectors search referenced records. Deletes display direct dependent records and require typing `LÖSCHEN`; database constraints and cascades apply.

Questions, choices, chapters, lessons, users, courses, orders, products, support, social records and all other model data can be managed at `/panel/<ModelName>`. Technical bookkeeping tables are advanced administration tools: changing one manually does not automatically reconcile every derived balance or invoke external services.

Content mutations bump lesson versions. Publishing a lesson requires reading content and questions with at least two choices and exactly one correct answer. If a child edit breaks a published lesson's answer structure, it returns to REVIEW.

## Test mode versus production

The shared password is a **test gate**, not proof of a person's administrator identity. Email-only test sign-in allows impersonation by design. Use only synthetic accounts in this mode.

In development test mode defaults on; `ENABLE_DEMO_AUTH=false` explicitly disables it. Production defaults off. Setting `ENABLE_DEMO_AUTH=true` explicitly enables the test behavior even on a test deployment. **Never enable it on a public production installation or an installation containing real users.** With it disabled, login uses verified Auth.js email magic links; panel authorization requires an actual verified account whose DB role is ADMIN. A test user session never grants panel access on its own.

For production: configure Supabase connection URLs, real AUTH_SECRET/AUTH_URL, SMTP and optionally payment credentials, set `ENABLE_DEMO_AUTH=false`, run migrations and deploy. See [DEPLOYMENT](docs/DEPLOYMENT.md).

## Content

Seed: 17 draft dental specialties, an introduction course, three original short anatomy lessons, badges, inactive example Pro products and current leagues. The anatomy examples cite ADA MouthHealthy. They are demonstration material, not a clinically validated curriculum and not copied from Dentigo. Other content can be created in the panel. Seeding is repeatable and does not overwrite existing records.

## Checks

```sh
npm run typecheck
npm test
npm run build
npm audit --omit=dev
```

Tests cover all-model CRUD, authorization, encrypted panel keys, secret redaction, demo registration/session behavior, verified-admin fallback, learning rewards and lesson UI. Integration tests use isolated PGlite databases; real Supabase/Vercel, SMTP and Stripe still need staging acceptance tests.

## Structure

- `src/app`: thin App Router pages and HTTP boundaries; `/panel` is outside the learner layout.
- `src/features`: feature components and schemas; `panel/` contains reusable administration components.
- `src/components/ui`: shared visual primitives and native modal dialog.
- `src/server/panel`: schema registry, scalar validation, CRUD, content integrity, encrypted keys and panel authorization.
- `src/server/services`: learning/access/reward logic.
- `src/server/routers`: typed tRPC API with server-side gates.
- `src/server/demo-session.ts`: isolated, switchable test login.
- `src/generated/panel-schema.json`: generated metadata; regenerate after schema edits.
- `prisma`: schema, migration and reusable idempotent seed.
- `tests`: unit, component and PostgreSQL-backed integration tests.

This release implements the requested mobile layout, desktop CRUD panel and test login. It is not a claim of exact parity with every locked Dentigo feature; [FEATURE-COVERAGE](docs/FEATURE-COVERAGE.md) records remaining product work.
